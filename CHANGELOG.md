# Changelog

All notable changes to `soroban-devkit-contracts` are documented here.

Format loosely follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). This project hasn't cut a tagged release yet, so everything below lives under **Unreleased**. See [ADDRESSES.md](ADDRESSES.md) for the full deployment history (every redeploy, with the real reason and the old address it replaced).

## Unreleased

### Known issues

- `cargo audit` reports one active advisory as of 2026-10-24: [RUSTSEC-2026-0387](https://rustsec.org/advisories/RUSTSEC-2026-0387), a timing-variability issue in `crypto-bigint` 0.5.5 (fix: `>=0.7.6`), pulled in transitively via `soroban-env-host` → `k256`/`ecdsa` → `elliptic-curve 0.13.8`, which pins `crypto-bigint = "^0.5"`. Confirmed with `cargo tree --target wasm32v1-none -i crypto-bigint`: this dependency never reaches the actual WASM build target at all — it's only part of `soroban-env-host`'s native-side ledger simulation used by `cargo test`, not anything compiled into a deployed contract. Confirmed no available `soroban-sdk` version fixes it either: `soroban-env-host` 29.0.1 (the current latest, pulled by `soroban-sdk` 29.0.1) still requires `elliptic-curve = "^0.13.5"`, the same constraint as the `27.0.1` this project pins. The real fix is upstream in RustCrypto's `elliptic-curve`/`k256`/`ecdsa` crates, several levels removed from anything this project's own `Cargo.toml` controls — not something a `soroban-sdk` version bump here would resolve. `paste 1.0.15` ("unmaintained", RUSTSEC-2024-0436) is the other `cargo audit` entry, with no CVE and no available replacement upstream in `soroban-sdk`'s dependency tree either.
- Every contract defines a typed error enum (`errors.rs`, a stable `u32` discriminant per variant) but most of them still aren't used in `lib.rs` — `vesting` is now fully converted across [#21](https://github.com/Raveu-lab/soroban-devkit-contract/pull/21) and [#22](https://github.com/Raveu-lab/soroban-devkit-contract/pull/22) (thanks [@de-authority](https://github.com/de-authority)); `token`, `access-control`, `upgradeable`, `multisig`, `oracle`, `dao-voting`, and `escrow` still raise raw `panic!("...")` strings instead of a typed, matchable error code.

### Added

- `[workspace.package] license = "MIT"` in the root `Cargo.toml`, inherited via `license.workspace = true` in all 9 contract crates. The root `LICENSE` file was added weeks ago specifically because the project claimed MIT everywhere but had no actual grant backing it; none of the 9 individual crates' own `Cargo.toml` ever got the matching `license` field, which is the metadata `cargo publish`/`crates.io` and per-crate license scanners actually read — confirmed by checking `cargo metadata`'s resolved `license` field for each package, which was `null` for all 9 before this.
- `event-rich.emit_muxed_address()` — this contract's whole purpose is exercising every XDR type `soroban-devkit-core`'s `EventDecoder` can decode, but muxed (`M...`) addresses had never actually been tested against a real contract call: `ArgEncoder`/`BindingGenerator` have encoded/typed them for a while, verified only against hand-built unit-test fixtures in `soroban-devkit-core`, never against a real deployed contract, because no function in this workspace had a parameter shaped to receive one. Confirmed live that `emit_address`'s plain `Address` parameter traps with `UnreachableCodeReached` for a muxed argument — `Address` genuinely cannot carry a multiplexing id; `MuxedAddress` is the dedicated type for that. `emit_address` itself is correct as written and needed no change; this is a new function, not a fix to an existing one.
- `token`, `access-control`, `upgradeable`, `multisig`, `event-rich` — the initial scaffold.
- `token`: `transfer_from` with real allowance decrement.
- `multisig`: `execute()` actually transfers tokens, instead of just recording state.
- `escrow` — time-locked escrow with dispute resolution (depositor/recipient/arbiter roles).
- `token/src/lib.rs`'s own module doc still listed "transfer, approve, transfer_from, mint, burn, clawback" after `burn_from` was added, an instance of this project's own "silently wrong" doc-drift pattern introduced by that very commit.
- `token.burn_from()` — the allowance-based burn, and the one function of SEP-41's ten-function `TokenInterface` this contract didn't implement, while `README.md` called it "a full SEP-41 fungible token" and `ARCHITECTURE.md` "a complete SEP-41 compliant fungible token". Any SEP-41 consumer calling `burn_from` on it failed. Decrements the allowance exactly as `transfer_from` does and emits the same `burn` event a direct burn emits, as the spec requires. Checked against the published SEP-0041 text rather than from memory — which also confirmed the existing event shapes are correct (no admin address in the `mint`/`clawback` topics, contrary to an older draft) and that `mint`/`clawback` are deliberately outside the interface. The one remaining deviation, `approve`'s `expiry_ledger` where the spec says `live_until_ledger`, is now documented rather than silently renamed: the name is part of the generated contract spec, so changing it would change the deployed interface.
- `demo/` — a walkthrough that calls the live testnet deployments and shows `vesting`'s cliff guard and `escrow`'s arbiter guard actually rejecting bad input, with real captured output rather than a unit test asserting they would. Runs through `sdev simulate`, so it needs no key, no funded account and no local build. It also makes the typed-error gap concrete side by side: `vesting` reports `Error(Contract, #7)` while `escrow` can only manage `VM call trapped: UnreachableCodeReached`.
- `access-control.role_admin()` — reads back the admin role configured for a role. `set_role_admin()` had no counterpart, unlike every other write in the contract (`grant_role`/`revoke_role` pair with `has_role`), so the permission graph could be written but never inspected and `require_role_admin`'s "no admin role set" panic was the only way to find out whether one existed.
- `vesting` — linear vesting with a cliff.
- `token`: `burn` and `clawback`.
- `oracle` — admin-published price feed with staleness checking.
- `dao-voting` — on-chain proposal and voting, one-address-one-vote.
- `.github/PULL_REQUEST_TEMPLATE.md` — no PR template existed in any of the three sibling repos; mirrors `CONTRIBUTING.md`'s existing "Pull Request Guidelines" as a checklist.
- `vesting` — property-based tests over `vested_at`'s invariants via `proptest` ([#22](https://github.com/Raveu-lab/soroban-devkit-contract/pull/22), external contribution — thanks [@de-authority](https://github.com/de-authority)): the vested amount stays within `[0, total_amount]`, is zero before the cliff, equals `total_amount` after `vesting_duration`, and is monotonic in `now`.

### Fixed

- `token.symbol()` returned a hardcoded `"DKT"` instead of the actually-initialized symbol.
- `upgradeable.migrate()` was not actually idempotent — calling it twice kept bumping the version.
- `access-control.initialize()` had no re-initialization guard, unlike every other contract — anyone could re-call it and hijack the super admin.
- `multisig.initialize()` didn't reject duplicate addresses in the signer list — `count_approvals()` sums one approval per *entry*, not per unique address, so a duplicate let one signer's approval count twice toward the threshold.
- `token`'s balance-moving functions (`mint`/`transfer`/`transfer_from`/`burn`/`clawback`/`approve`) didn't reject non-positive amounts — a negative amount could flip a transfer's arithmetic direction and let a caller mint themselves funds while draining the recipient.
- `multisig.propose()` didn't reject a non-positive amount, for the same reason.
- Persistent-storage TTL wasn't managed anywhere — `oracle`, `access-control`, `dao-voting`, `escrow`, `multisig`, and `vesting` each got this fixed per-contract: a default write's TTL (a few thousand ledgers) is nowhere near the network max (several million), so an untouched entry would eventually get archived from disuse, even though nothing about it changed.
- The same gap existed for **instance** storage, more severely — losing an instance makes the whole contract inoperable, not just one entry. Fixed across `oracle`, `access-control`, `token` (which had *no* TTL management at all before this), `multisig`, `upgradeable`, `dao-voting`, `escrow`, and `vesting`. `upgradeable`'s case was the worst: `upgrade()`/`migrate()` are the only way to ever fix a deployed contract, and both are admin-gated, reading the admin from the instance.
- `token.approve()`'s `expiry_ledger` (an absolute ledger sequence) was passed straight into `extend_ttl()`'s relative-count parameter, so an allowance silently outlived its stated expiration. `approve(0)` — SEP-41's way to revoke an allowance — was also rejected by the blanket positive-amount guard.
- `dao-voting.propose()` had no guard against `voting_duration == 0`, unlike `vesting`'s equivalent field — a proposal with `voting_duration=0` got `deadline = now`, silently un-votable by anyone, forever.
- The bug-report issue template's "Which contract?" dropdown only listed 5 of 9 contracts.
- The repo had no actual `LICENSE` file — the README's badge and its "MIT — see [LICENSE](LICENSE)" line both linked to a file that didn't exist, a dead link since this repo's creation. The project claimed to be MIT-licensed and open source; there was never an actual license grant for the code, only prose about one.
- `event-rich` never emitted `scvU256`/`scvI256`/`scvTimepoint`/`scvDuration` events, even after `soroban-devkit-core`'s decoder gained real support for all four — despite this contract's entire purpose being coverage of every XDR type the decoder can handle.
- `vesting`'s panic paths raised raw strings instead of its own typed `VestingError` ([#21](https://github.com/Raveu-lab/soroban-devkit-contract/pull/21) and [#22](https://github.com/Raveu-lab/soroban-devkit-contract/pull/22), external contributions — thanks [@de-authority](https://github.com/de-authority)).
- `access-control`'s `RoleAdmin` mapping lives in instance storage but was the only accessor pair in `storage.rs` that never extended the instance TTL — the earlier instance-TTL fix covered `SuperAdmin` and missed it. No existing call path was actually at risk, since `set_role_admin`/`require_role_admin` both read `SuperAdmin` first and that extends; the new `role_admin()` getter is the first path to reach instance storage without doing so, which is what makes the gap load-bearing rather than merely inconsistent.
- `escrow.deposit()` never checked that the arbiter was actually a third party, and an arbiter who is also a party defeats the entire escrow. Once an escrow is `Disputed`, only the arbiter may release or refund, and the `Active` arm — with it the timelock path anyone could use after `release_time` — becomes unreachable. So a depositor who names themselves arbiter can dispute their own escrow and immediately refund themselves, at any time, with no recourse for the recipient; naming the recipient as arbiter is the mirror image. Verified end to end against the real contract before fixing. Both are now rejected at deposit. `depositor == recipient` is still allowed: locking your own funds until `release_time` behind a neutral arbiter is a legitimate self-timelock, and only the arbiter's neutrality is a security property. Same class as the earlier `multisig.initialize()` duplicate-signer fix.
- `vesting.create_vesting()` validated `total_amount` and `vesting_duration` but never checked `cliff_duration` against `vesting_duration`. A schedule whose cliff outlasts its own vesting window was accepted, after the token transfer had already pulled the depositor's funds, and then behaved nothing like a vesting schedule: `vested_at` returns 0 for the entire cliff, including the whole stretch past `vesting_duration` where the curve says fully vested, then jumps straight to `total_amount` the instant the cliff clears. The linear portion is unreachable, so `vesting_duration` silently means nothing and the contract becomes a cliff-lock wearing a vesting schedule's shape. Rejected at creation now, with `cliff_duration == vesting_duration` still allowed as a legitimate pure-cliff schedule.

### Changed

- Upgraded to `soroban-sdk` 27.0.5.
